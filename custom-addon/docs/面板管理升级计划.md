## 二、已定决策(不再重复讨论)

| 决策 | 结论 |
|---|---|
| 数据 SSOT | 面板 SQLite(8318 管理舱)唯一主库;`06-卡密管理` 的 JSON 文件是导出物/冷备份 |
| 三状态模型 | `lifecycle`(人工:unused/in_use/sold/archived)+ `health`(探活自动写)+ `auth_state`(推导:authorized/missing_mailapi_url/needs_reauth) |
| 健康分类 | ok / depleted / token_expired / token_invalidated / token_invalid / workspace_deactivated / err / unknown |
| 检测策略 | 纯手动(检测选中/检测当前筛选),间隔 3s,可中断,429 退避 60s,无定时任务 |
| 已检测口径 | `quota` 与 `nextTime` 均有值即为已检测；它不是健康正常的同义词 |
| Token 刷新 | 库存页手动选择记录后逐个刷新；成功回写新 token 并重置健康为 `unknown`；`invalid_grant` 标记 `needs_reauth` |
| 拓扑 | 本 fork 项目统一监听 8318；数据管理面板与日常代理共用同一端口，面板 SQLite 是唯一主库 |
| 批次建模 | `batches` 表,从 `source_batch` 字符串解析编号/日期/订单号/件数/价格;渠道平铺字段,不建树 |
| 商业功能 | 不做(NexusVault 的资金账户/自动补池/结算/商品等) |

## 三、Phase 1-④:部署 / 回收 ✅

**目标**:把「生成配额」升级为完整的「账号部署」闭环——从库存选号 → 生成凭证文件落到指定 auth 目录 → 记录部署状态;反向把失效账号从 auth 目录回收回库存。

### 3.1 后端(数据管理 API 新增两个动作)

- [x] `POST /v0/management/data-records/deploy`
  - 入参:`{ ids: [], target: "local" | "official" | <白名单 key> }`
  - 行为:按选中记录生成 Codex 凭证 JSON(`<email>.json`,复用现有 `generate_quota_files` 的字段映射)写入目标目录;同邮箱已存在则覆盖
  - 回写:每条记录 `lifecycle = in_use`、`deployed_at = <now>`、`deploy_target = <target>`
  - 响应:`{ deployed, target, dir, files[] }`
- [x] `POST /v0/management/data-records/recycle`
  - 入参:`{ ids: [], target: ... }`(或按 email)
  - 行为:删除目标目录中对应的 `<email>.json`;回写 `lifecycle = unused`、清空 `deployed_at`
  - 响应:`{ recycled, files[] }`
- [x] 目标目录白名单(硬编码于后端,拒绝任意路径,防路径穿越):
  - `local`:本仓库 `.cli-proxy-api/`
  - `official`:`C:\Users\802165\CLIProxyAPI\.cli-proxy-api\`(官方 auth 目录)
  - 白名单后续可在 config 或常量中扩充
- [x] 保留现有 `generate-quota` 端点向后兼容(内部复用 `deploy/local`;返回旧响应字段)

### 3.2 前端(库存页)

- [x] 库存页新增目标目录下拉(本仓库 / 官方 auth 目录),旧入口文案收敛为「兼容生成」
- [x] 选中 → 部署 → 结果弹窗(显示目标目录与文件清单)
- [x] 勾选已部署记录 → 「回收选中」按钮(需确认弹窗)
- [x] `deployed_at` / `deploy_target` 通过动态列显示(排序后议)

### 3.3 验收标准

## 四、Phase 1-⑤:格式转换工具页 + 重授权登记 ✅

### 4.1 格式转换工具页(面板新入口「工具」)

**范围(已裁剪)**:仅三种转换,其余格式(Cockpit/9router/AxonHub 等)等真实需求再加。

- [x] `txt → CPA`:原版卡密 txt 中的 JSON 对象行解析为 CPA JSONL
- [x] `CPA → sub2api`:CPA JSON/JSONL/数组转 sub2api bundle JSON
- [x] `sub2api → CPA`:外部 sub2api bundle 的 `accounts[].credentials/extra` 转 CPA JSONL
- [x] 实现形态:**后端转换动作**(POST /v0/management/data-records/convert,`{ from, to, content }` 返回转换结果 + 可下载),前端独立工具页(输入框/文件上传 + 输出框 + 下载按钮),遵循「与库存数据隔离」原则:转换页不读不改库存,只处理用户显式粘贴/上传的内容
- [x] 转换为纯函数,配单测(样本输入 → 期望输出)

说明:按当前已观察到的 JSON 对象行/JSONL/sub2api bundle 形态做最小可用解析;Cockpit/9router/AxonHub 等格式继续等真实样本再加。

### 4.2 重授权登记

**定位**:不做代登录(NexusVault 式服务端重授权不符合本地架构);只做「重授权产物登记」——你用本地 OA 授权工具链跑完后,把产物导入面板,面板解析并回写。

- [x] `POST /v0/management/data-records/register-reauth`:上传重授权产物 JSONL
  - 按邮箱匹配库存记录(复用 dedupe 合并语义:产物字段更新,不覆盖库存中更新的活字段)
  - 解析并回写:`reset_expired_at`(重置后过期日期)、`reauth_at`(本次重授权日期)、新 access_token/refresh_token
  - `auth_state` 翻回 `authorized`;`health` 重置为 `unknown`(等下次检测)
- [x] 前端:库存页「登记重授权」入口跳转工具页;工具页「上传重授权产物」按钮 + 文件上传 + 结果报告(成功/未匹配/字段缺失条数)
- [x] 字段口径:`expired` 写入 `reset_expired_at`;`reauth_at` 有传则保留,无传则取登记时间;`last_refresh` 原样回写
- [x] 未匹配邮箱的产物行:可选「作为新记录入库」(默认开)

## 六、风险与纪律(长期有效)

1. **非空库导入永远带 dedupe**(面板按钮已默认;命令行务必带 `?dedupe=1`),导错可重复执行幂等修复;
2. 每次大批量导入/部署后跑一次 `backup-data.ps1`;
3. 本 fork 项目统一使用 8318，数据管理入口只访问同一实例的 `/data-mgmt/`；
4. 改 Go 补丁面后必须重新编译并重启 8318,同时同步 `modified-files/` 归档;
5. `data/`、`custom-addon/`、`backup/` 靠 `.git/info/exclude` 隐身,换机需手动拷贝。
